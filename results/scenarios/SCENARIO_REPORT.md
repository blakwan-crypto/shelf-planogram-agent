## Analyzed failure cases

### Failure case 1 — truncated JPEG (`corrupt/corrupt.jpg`)
- **Input:** shelf3.jpg cut to its first 800 bytes. The JPEG header (with the 1280x960 dimensions) is intact; the scan data ends mid-way.
- **Where it failed:** Stage 2 (preprocess). PIL's `verify()` hit the short data stream and raised.
- **What the pipeline did:** returned a `RejectedInput` message (`corrupt or unreadable image (Truncated File Read)`), logged the hand-off to the trace, and moved on. Batch exit code 0 — no crash.
- **Why it matters:** one bad photo must not sink the whole batch — the agent records WHY and keeps going.

### Failure case 2 — out-of-bounds image sizes (`tiny/` and `oversized/`)
- **Input:** a 48x36 thumbnail (below the 64-px minimum) and an 8100-px-wide upscale (above the 8000-px maximum).
- **Where it failed:** Stage 2 (preprocess) — the size check reads only the image header, before any model work.
- **What the pipeline did:** rejected both (`too small (48x36)`, `too large (8100x9437)`). The detector was never called — no wasted compute, no crash.
- **Why it matters:** the bounds are a cheap guard against icons, mistakes and memory hogs.

### Failure case 3 — an image with no shelf (`non_shelf/parking_lot.jpg`)
- **Input:** a real aerial photo of an empty parking lot (Wikimedia Commons) — no shelves anywhere.
- **What the pipeline did:** processed it without crashing — **0 product detections**. The AnalystAgent then marked every planogram slot `out_of_stock` (32 work orders) because it assumes a shelf is present.
- **Honest limitation (not a crash):** there is no 'is this even a shelf?' gate. On a genuinely non-shelf photo the agent reports everything as out of stock. A cheap fix: if detections == 0, emit a 'no shelf detected' verdict instead of 32 restock tasks.

## Known robustness gaps found by this suite (NOT fixed — outside its ownership)

These bugs live in `agents/` and `tools/`, which this scenario suite is not allowed to edit. They are recorded here (with evidence) so the repo owner can fix or report them.

1. **Truncated JPEGs ≥ ~1000 bytes slip past Stage 2 and crash the detector.**
   - PIL's `verify()` checks only the JPEG header segments, so a file cut at 2000 bytes still passes preprocess (evidence: `corrupt/truncated_2000bytes.bin` — it looks like a valid 1280x960 JPEG).
   - The detector then runs `self.model.predict(image_path, ...)[0]` (`tools/detector.py`); ultralytics cannot read the image, returns an empty list, and `[0]` raises `IndexError: list index out of range`.
   - That is why `corrupt/corrupt.jpg` is cut at 800 bytes instead: still a genuinely truncated JPEG, but one Stage 2 rejects cleanly — so the scenario proves graceful failure rather than the bug.
   - Suggested fix: in `tools/detector.py` guard the result (`results = self.model.predict(...); if not results: return []`).
2. **TaskAgent never creates its `tasks/` output folder.**
   - `TaskAgent.act()` writes work orders into `out_dir/tasks/` without creating it (`agents/task_agent.py`). The repo's baseline `results/tasks/` only worked because it already existed on disk — a fresh `--out` folder crashes with `FileNotFoundError` on the first processed image.
   - The scenario runner pre-creates `images/` and `tasks/` (the same layout as `results/`) so scenario runs exercise image handling, not this bookkeeping crash.
   - Suggested fix: create `out_dir/tasks/` in `TaskAgent.__init__`.
